# Fixxir UI and UX audit

Reviewed 30 September 2026. The strongest opportunities are to protect form progress, make service promises concrete, shorten the homepage, and make the repair journey visually consistent.

**Scope and evidence**

Reviewed the homepage, all six repair-request steps, confirmation-page source, shared styles, and intake validation. Inspected the supplied screenshots and rendered the local app in Chrome at desktop (1440px), tablet (768px), mobile (390px), and small mobile (320px) widths. Findings below distinguish reproduced behavior from source observations and design proposals.

No repair requests, emails, or WhatsApp messages were sent. Successful persistence and email delivery were not tested. The local Next.js server does not run the Cloudflare Pages functions, so the local unavailable-intake screen is not evidence that production intake is disabled. The current implementation does, however, use that same screen for loading, network failure, and unavailable intake. This was a usability review, not a complete accessibility conformance or performance audit.

**What is already working**

- The navy and blue identity, prominent repair CTA, and phone/laptop categories communicate the service clearly.
- At 390px, the hero actions are visible in the first viewport. No horizontal overflow appeared on the homepage at the four checked widths or the 390px form/review screens.
- The mobile quick-action bar appears after scrolling past the hero. The menu moves focus to its close button and closes with Escape.
- The form supports a custom device and an unknown model, useful when someone cannot identify a broken device.
- Contact details, support hours, and the statement that submitting a request does not authorize a repair are useful reassurance.
- Native FAQ disclosures and reduced-motion styling provide a good accessibility foundation.

**Prioritized findings and recommendations**

1. **High — Back loses newly entered form data.** Reproduced: enter name, phone, and email on step 3; press Back; continue to step 3 again. All three values are empty. Steps keep temporary state and save it only on Continue; a refresh also has no draft recovery. Save changes in shared state as they happen. Consider an expiring session draft with a clear reset action. Acceptance check: edit any field, navigate backward and forward, and retain the latest value. Evidence: [contact-step state](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:361), [wizard state](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:673).

2. **High — Users can complete a form that cannot be submitted.** Reproduced in the unavailable local state: all six steps remain interactive, progress reaches 100%, and the final button is disabled. An initial `false` flag also shows “not active yet” before the availability check finishes; a network error receives the same message. Introduce separate loading, available, unavailable, and retryable-error states. When intake is unavailable, show prominent WhatsApp and call actions before asking for personal details. Evidence: [availability state](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:674), [disabled submission](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:659).

3. **High — Validation lets errors travel to the end of the journey.** Reproduced: `abc` is accepted as a phone number and appears on the final review. The server later validates the number and returns a generic required-details error. Several steps use browser alerts instead of errors beside the relevant control. Validate phone input before advancing, accept common local/international formatting, and align client/server rules. Show an inline correction, associate it with the field, and focus the first invalid input. Evidence: [contact validation](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:363), [server error](/Users/dinny/Documents/Fixxir/fixxir-web-app/functions/api/repair-requests.ts:259). This follows [W3C form-notification guidance](https://www.w3.org/WAI/tutorials/forms/notifications/).

4. **High — Hero imagery suggests a tracking feature that is unavailable.** The supplied screenshot and rendered hero depict a repair dashboard with milestone tracking, while the page says online tracking is unavailable. Copy also promises updates while other sections tell customers to ask for them. Use actual service photography or imagery representing the current process. State the real update channel and who initiates contact. If milestone WhatsApp updates are operationally feasible, they would directly support the service promise. Evidence: [hero image](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/components/HeroSection.tsx:14), [tracking disclaimer](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/components/TrustPrivacy.tsx:50), [update wording](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/components/TrustSignals.tsx:6).

5. **High — The tablet hero places copy over detailed imagery.** Observed at 768px: the heading, paragraph, and pickup note overlap the phone interface. The desktop gradient becomes too transparent behind the text at this width. Give tablet its own layout: stack copy and image, move the image out of the text area, or use an opaque text surface until the desktop split has sufficient room. On mobile, replace the heavily blurred dashboard backdrop with a quieter branded background or a separate image. Evidence: [responsive hero layers and copy width](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/components/HeroSection.tsx:12).

6. **High — Review is incomplete and hard to edit.** Reproduced: the final summary omits email, problem details, and handoff preference, and displays `nourgency` instead of “No urgent deadline.” Users must traverse earlier steps to correct information. Show every relevant supplied value, human-readable labels, and an Edit action for each group that returns to review afterward. Keep the no-authorization explanation. Evidence: [review content](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:607).

7. **High — Accessibility needs a focused pass.** Source review found name, phone, address, and details labels without explicit control associations; issue/handoff/timing choices lack accessible selected states; step transitions scroll without moving focus to the new heading. The homepage lacks a main landmark/skip link, and the mobile drawer lacks modal semantics. Use associated labels, native radio groups, an accessible step announcement, and a consistent page heading. Add a named modal dialog with appropriate background isolation. Separately, the rendered 14px WhatsApp link is approximately **3.22:1 against white**, below the 4.5:1 requirement for normal text: darken it. Evidence: [form labels](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:382), [step transitions](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:703), [link color](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:793), [menu](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/page.tsx:117). See [W3C contrast guidance](https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum) and [control labeling](https://www.w3.org/WAI/tutorials/forms/labels/).

8. **Medium — The homepage is long relative to the information it provides.** Measured approximately 6,762px at desktop width and 9,925px at 390px. Trust Signals, Problem Differentiation, and Trust Privacy overlap in purpose. Services appear after two reassurance sections. Merge repeated promises into a compact proof strip and put service selection earlier. Reduce the repeated 112px desktop section padding where sections are sparse. Suggested order: hero → compact proof → services → process → confirmed terms and FAQ → business → final action/contact. Evidence: [page composition](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/page.tsx:183).

9. **Medium — The empty review section weakens the trust story.** The “Verified reviews coming soon” block occupies about 542px of the desktop page without providing a customer experience to assess. Remove it until genuine reviews exist, or replace it with verifiable proof such as the actual workshop, a sample quote, or an explained quality-check process. Avoid a verification-style badge on an empty state. Evidence: [reviews placeholder](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/components/ReviewsSection.tsx:3).

10. **Medium — Core service questions remain unanswered.** Warranty, access to device data, parts, diagnosis costs, turnaround, and pickup often lead to “ask us.” Lagos and Abuja are advertised, while only a Lagos workshop address and a free-text area field are provided. Publish confirmed terms and clarify coverage separately by city. Explain which prices/terms depend on diagnosis and what will be supplied in the quote. Do not introduce an unverified warranty duration or response promise. Evidence: [trust questions](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/components/TrustPrivacy.tsx:10), [FAQ](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/components/FAQSection.tsx:13), [coverage claim](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/components/HeroSection.tsx:25).

11. **Medium — The primary action loses prominence after the hero.** Desktop navigation contains section links and Contact but no repair CTA. The bottom repair bar exists only below 640px, leaving tablet users without an equivalent persistent action. Add a compact “Start a repair” button to the desktop/tablet header. Keep WhatsApp secondary and retain the mobile bar's dismiss action. Evidence: [navigation](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/page.tsx:87), [mobile bar breakpoint](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/page.tsx:158).

12. **Medium — The form feels visually disconnected from the landing page.** The homepage uses navy text, the brand blue, generous rounded shapes, and a branded header. Intake switches to brighter default blue, gray form cards, smaller corner radii, and no persistent brand header; submission becomes green. Use shared color, button, input, spacing, and radius tokens across all three pages. Keep a small Fixxir header and stable help placement throughout. Split the cramped mobile support paragraph into readable contact actions and a separate hours line. Evidence: [global tokens](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/globals.css:3), [form shell](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:749), [support text](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:787).

13. **Medium — Device selection has an unreliable fallback and loses entry context.** Reproduced: select a custom brand and type a model; the loading spinner remains visible because custom brands bypass lookup. Source also leaves old model results available after choosing a custom brand. Reset dependent results/loading and use a plain model field for manual brands. Complete keyboard behavior for the searchable lists. Separately, “Start Phone repair” and “Start Laptop repair” lead to the same empty form: carry that choice forward. Evidence: [model lookup](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:115), [custom brand](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:148), [service links](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/components/ServicesSection.tsx:16).

14. **Medium — The journey can ask less and explain more.** Timing has its own screen, the address field appears even for drop-off, and progress shows 100% before a request has been submitted. Test a four-stage structure: Device and issue → Contact → Handoff and timing → Review. Show named stages instead of an ambiguous percentage. Ask city/coverage before a detailed address and make the address conditional on pickup. Consider offering photo sharing after submission so a request reference can accompany the message. These are design proposals; their effect on completion should be measured. Evidence: [location](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:436), [timing](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:524), [progress](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/page.tsx:764).

15. **Medium — Confirmation needs clearer ownership of the next step.** Source says the team will contact the customer, then says arrangements will be confirmed “when you contact us.” Email wording exposes internal states such as “accepted for sending” and “could not be queued.” State who acts next, through which channel, and within a response window the business can support. Add a compact request recap and a copy-reference control. For email failure: “Your request is saved. We couldn't send your confirmation email.” Do not imply inbox delivery from provider acceptance. Evidence: [confirmation copy](/Users/dinny/Documents/Fixxir/fixxir-web-app/app/repair/request/success/page.tsx:42).

**Smaller polish improvements**

- Separate the hero pickup statement into complete sentences: “Pickup and return in selected areas. Contact us to confirm availability.”
- Replace the unexplained green WhatsApp dot with an icon or explicit support hours; the dot can be read as live availability.
- Replace “QA” with “Quality check,” and make business CTA wording match its actual WhatsApp destination. Both current business buttons initiate the same conversation.
- Keep the strong headline but shorten its supporting paragraph so the first action arrives sooner on small phones.
- Give request and confirmation pages distinct browser titles.

**Suggested delivery order**

1. Fix data retention, availability states, validation, review details, and the custom-model loading state. These affect task completion directly.
2. Fix tablet readability and accessibility, align hero imagery with the service, and remove the empty reviews block.
3. Consolidate landing-page content, unify shared styling, add the header CTA, and clarify coverage and operating terms.
4. Trial the shorter wizard and improved confirmation experience. Measure request starts/completions, abandonment by step, validation failures, and WhatsApp exits without recording the content of personal fields.

**Validation after changes**

Repeat the backward/forward edit test across every step, refresh/recovery, invalid-phone correction, custom-brand entry, keyboard-only navigation, availability-loading/error recovery, and review/edit flow. Recheck 320px, 390px, 768px, and desktop layouts. Use the Cloudflare local runtime or a test environment for successful submission and email-failure scenarios; the Next.js development server alone cannot validate that backend flow.
